# Фільтрація діагностик по переліку файлів (`--file-list`)

Дата: 2026-06-15
Статус: затверджено до планування

## Проблема

Під час пакетного аналізу (`analyze`) інколи потрібно отримати діагностики лише для
певного набору файлів (наприклад, змінених у PR), але при цьому зберегти коректність
крос-файлових перевірок (як-от «невикористаний метод», «невідомий метод»). Простий
аналіз тільки переданих файлів зламав би крос-файловий контекст, бо індекс символів
будувався б по неповному набору.

Потрібна додаткова опція: **повне сканування проєкту заради крос-файлового контексту,
але обчислення та видача діагностик лише по переданому переліку файлів**.

## Обрані рішення

- **Режим**: тільки CLI `analyze` (`AnalyzeCommand`). LSP-режим не зачіпається.
- **Передача переліку**: новий CLI-прапор `--file-list` (короткий `-fl`), що вказує на
  текстовий файл зі шляхами (один на рядок).
- **Формат шляхів**: підтримка і відносних, і абсолютних шляхів із нормалізацією.
- **Розміщення**: тільки CLI-прапор (не в `.bsl-language-server.json`), бо перелік
  файлів — властивість конкретного запуску.
- **Підхід реалізації**: фільтр у `AnalyzeCommand` (Підхід A) — мінімальна площа змін,
  повне сканування лишається незмінним.

## Архітектура та потік

Зміни локалізовані в `AnalyzeCommand.call()`
(`src/main/java/com/github/_1c_syntax/bsl/languageserver/cli/AnalyzeCommand.java`,
зараз рядки 181–207) плюс новий хелпер для читання/нормалізації списку.

Поточний потік:

1. `allFiles = BSLFiles.listBslFiles(srcDir, configuration.getExcludePaths())`
2. `serverContext.populateContext(allFiles)`
3. Цикл по `allFiles` → `getFileInfoFromFile` → `documentContext.getDiagnostics()`
4. `aggregator.report(...)`

Новий потік:

1. `allFiles = BSLFiles.listBslFiles(...)` — **без змін** (усі файли проєкту).
2. `serverContext.populateContext(allFiles)` — **без змін** (повний крос-файловий
   індекс будується по всьому проєкту).
3. **Нове**: якщо задано `--file-list`, обчислити
   `filesToAnalyze = allFiles ∩ requestedFiles`; інакше `filesToAnalyze = allFiles`.
4. Цикл обчислення `fileInfos` і прогрес-бар працюють по `filesToAnalyze`.
5. `aggregator.report(...)` — звіт містить `FileInfo` лише для відфільтрованих файлів.

### Чому це коректно для крос-файлових перевірок

У `ServerContext.populateContext(Collection<File>)` для кожного файлу викликається
`rebuildDocument`, що тригерить `DocumentContextContentChangedEvent`; на нього підписаний
`ReferenceIndexFiller`, який наповнює `ReferenceIndex`. Лише після цього викликається
`tryClearDocument` (звільняє AST, але записи в `ReferenceIndex` лишаються, бо це singleton).

Отже крос-файловий індекс будується по **всьому** проєкту незалежно від того, для яких
файлів ми потім рахуємо діагностики. Діагностики для файлів зі списку отримують повний
крос-файловий контекст.

## Опція CLI

```
-fl, --file-list <path>
```

- Шлях до текстового файлу: один шлях на рядок.
- Порожні рядки та рядки, що починаються з `#`, ігноруються (CI-коментарі).
- Якщо сам файл-список не існує — помилка та `return 1` (узгоджено з наявними перевірками
  шляхів у `call()` для `workspaceDir` / `srcDir`).
- Прапор не задано → поточна поведінка (аналізуються всі файли). Зворотна сумісність.

## Нормалізація та зіставлення шляхів

Новий хелпер (напр. `FileListReader` у пакеті `cli` або `utils`):

- Читає рядки файлу-списку; trim; пропускає порожні рядки та `#`-коментарі.
- Для кожного рядка: якщо шлях абсолютний — береться як є; якщо відносний — резолвиться
  відносно `workspaceDir` (`-w`). Це відповідає типовому виводу `git diff --name-only`.
- Нормалізація кожного шляху через `Absolute.uri(...)` → формується `Set<URI>`.
- `filesToAnalyze` = ті елементи `allFiles`, чий `Absolute.uri(file.toURI())` міститься
  в наборі.

### Крайові випадки

- **Незматчені записи** (виключені `excludePaths`, неіснуючі, не `.bsl/.os`, поза
  `srcDir`): логуються як `warn` і пропускаються. Без мовчазного відкидання.
- **Порожній результат після фільтрації**: `warn` + порожній звіт, `return 0` (валідний
  кейс «нічого не змінилось»).
- **Файл-список відсутній на диску**: `error` + `return 1`.

## Тестування

- **Unit-тест хелпера** (`FileListReaderTest`): відносні/абсолютні шляхи,
  коментарі та порожні рядки, неіснуючий запис, нормалізація до `URI`.
- **Інтеграційний тест `AnalyzeCommand`** на фікстурі з крос-файловою діагностикою:
  запуск із `--file-list` на один файл → у звіті діагностики лише цього файлу, **і**
  крос-файлова перевірка дала коректний результат (підтверджує, що індекс побудовано по
  всьому проєкту, а не лише по переданому файлу). Орієнтуватись на наявні тести
  `AnalyzeCommand`.

## Поза межами

- Підтримка glob-шаблонів у файлі-списку.
- Конфігурування через `.bsl-language-server.json`.
- Підтримка в LSP-режимі (фільтрація `publishDiagnostics`).
